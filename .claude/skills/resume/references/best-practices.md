# エンジニア職務経歴書 ベストプラクティス チェックリスト

audit モードの採点基準。各項目を ✅（満たす）/ ⚠️（部分的）/ ❌（不足）で評価する。
出典: doda・リクナビNEXT・JAC Recruitment・Qiita 等の職務経歴書ガイド（2025〜2026）。

評価のやり方: セクション 1〜4（構成・実績・分量・トレンド）は本文を読んで内容面を判断する。
セクション 5（文章品質）は `npm run lint` の結果を根拠にする（手動で重箱の隅をつつかない）。

## 1. 必須セクション

- [ ] **職務要約**: 冒頭に 3〜4 行で「誰が・何を・どんな成果で」を要約しているか
- [ ] **職務経歴（詳細）**: 各社/プロジェクトごとに、概要・自分の役割・担当フェーズ・
      チーム/プロジェクト規模・技術スタックが揃っているか
- [ ] **主な実績**: プロジェクトごとに具体的な実績が挙がっているか
- [ ] **活かせる経験・スキル**: 技術スタックを俯瞰できる一覧（言語/FW/DB/インフラ等を
      経験年数やレベル感とともに）があるか
- [ ] **保有資格**: 取得年月とともに記載されているか
- [ ] **自己PR**: 強み・志向を、客観的な根拠（実績）と結びつけて書いているか

## 2. 実績の質（STAR ＋ 定量化）

- [ ] **STAR で記述**: Situation（状況）/ Task（課題）/ Action（行動）/ Result（結果）が
      読み取れるか
- [ ] **定量化**: 成果が数字になっているか。例:
  - 削減率・改善率（例: 処理時間 4h→2h（50%削減））
  - 前年比・成長率、コスト削減額
  - 処理件数・データ規模・利用者数・チーム人数
  - リリース頻度・障害率・テストカバレッジ
- [ ] **客観性**: 主観的形容（「大幅に」「劇的に」）に頼らず、事実と数値で語っているか
- [ ] 誇張・推測値ではなく、実際に説明できる数値か

## 3. 分量・読みやすさ

- [ ] 分量の目安に合っているか（経験 3 年未満 ≒ 2 ページ / 5 年以上 ≒ 3〜4 ページ相当）
- [ ] 見出し・箇条書き・テーブルで構造化され、流し読みで要点が掴めるか
- [ ] 時系列・粒度が職歴間で揃っているか

## 4. 2026 年トレンド

- [ ] **AI 活用経験**: AI を「開発パートナー」として使い生産性を上げた経験
      （コード生成・レビュー・調査・自動化など）に言及があるか
- [ ] 直近で需要の高いスキル・領域（クラウド、スケーラビリティ等）が現職に反映されているか

## 5. 文章品質（textlint と整合）

- [ ] 用語が統一されているか（表記ゆれ・全半角・カタカナ語）
- [ ] 一文が長すぎないか（textlint の sentence-length 上限と整合）
- [ ] 冗長表現・二重否定・助詞の重複がないか

## 採点の出し方

各セクションを上から評価し、**❌ → ⚠️ の順に優先度を付けて**改善提案する。
提案は「現状 → 改善案（具体的な文面）」の形で示し、ユーザーの同意を得てから本文へ反映する。
