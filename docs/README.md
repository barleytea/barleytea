<h2 id="職務要約">職務要約</h2>

2017年からソフトウェアエンジニアとして、グループウェア、医療・製薬向けサービス、ポイントサイトの開発に携わってきた。Java／SpringとGoを中心に、バックエンドの設計・実装・運用を担当している。

業務要件が曖昧な場面では、関係者と仕様を整理し、テストや運用フローまで含めて仕組みに落とし込む。Goによる集計ツールの再実装では、処理時間を4時間から2時間に短縮した。

現在は東急カードポイントサイトの内製化に向け、夜間バッチ処理と実行基盤の設計・実装を担当している。

<h2 id="主な実績">主な実績</h2>

- **夜間バッチ基盤の設計・構築:** 後続業務を整理し、GoとAWSを使ったバッチ処理と実行基盤を新たに構築
- **集計時間を50％短縮:** 集計ツールをGoで再実装し、実行時間を4時間から2時間に短縮
- **勤怠計算の改修を安全に:** JUnitのテストと業務側の確認手順を整え、計算ロジックの回帰を検知できる状態にした
- **サブスクリプション決済を導入:** Stripeを選定・実装し、決済失敗時の運用フローも整備

<details class="web-detail">
<summary>実績の詳細</summary>
<div>
<h4>Stripeでサブスクリプション決済を導入</h4>
<p>
クレジットカードによる有料プランを導入するため、ZuoraとGMOペイメントゲートウェイを比較した。
費用と設定の柔軟性を踏まえてStripeを選定し、事業側と料金・契約サイクルを整理した。
Stripe APIで決済基盤を実装した。
SpreadsheetとGASで決済に失敗した利用者の情報を自動収集する仕組みも整えた。
運用担当者向けの対応フローも策定した。
</p>
<h4>勤怠計算ロジックのテストを整備</h4>
<p>
仕様を把握する担当者がおらず、画面から1か月分の勤務情報を入力しないと計算結果を確認できない状態だった。
計算メソッドにJUnitテストを追加し、既存の挙動を確認できるようにした。
勤務条件と計算結果を出力する形式も整え、事業側と仕様を確認しながら改修できるようにした。
</p>
<h4>PDF帳票出力の共通モジュールを設計</h4>
<p>
病院ごとの帳票要件に対応するため、帳票作成サービスSVFを導入した。
勤怠データをSVF APIへ渡すインターフェースを共通化し、必要なフィールドを持つBeanを定義すれば帳票を追加できるようにした。
Marker Interfaceを実装したBeanに必要なフィールドを定義することで、SVF固有の処理を意識せずに帳票を追加できるようにした。
別チームの開発者が帳票ごとのデータ計算に集中できる構成にした。
</p>
<h4>BI向けETLの運用を改善</h4>
<p>
MongoDBからBI用PostgreSQLへ全件転送していたため、処理に約10時間かかり、データ量の多いコレクションではタイムアウトも発生していた。
勤怠関連のコレクションを別のETLに分け、特に大きいコレクションは3分割して投入する方式に変更した。
先に必要となるデータを利用できるようにし、対象処理のタイムアウトを解消した。
</p>
<h4>月次アクティブユーザー集計を高速化</h4>
<p>
ローカルDBへのデータ取り込みと集計に約4時間かかり、後続の手作業にも負荷がかかっていた。
不要なデータ取得を削り、JavaScriptで実行していた集計をGoのCLIツールとして再実装した。
MongoDBの結合処理を見直し、最終成果物の作成と実行環境のコンテナ化も行った。
データ取り込みは約2時間から約1.5時間、集計は約2時間から約10分に短縮し、全体の作業時間を約4時間から約2時間に短縮した。
</p>
</div>
</details>
